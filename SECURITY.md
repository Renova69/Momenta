# Security Policy

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Use GitHub's private vulnerability reporting, which is enabled on this
repository:

> **Security** tab → **Report a vulnerability**

That opens a private channel visible only to the maintainers. If you cannot use
it for any reason, open a normal issue saying only that you have a security
report and asking for a contact address — no details.

### What helps

- What an attacker can do, not only what looks wrong.
- The smallest set of steps that reproduces it.
- The commit or version you tested against.

### What to expect

This is a small project, not a funded security programme. There is no bounty.
You will get an acknowledgement and an honest answer about whether and when it
will be fixed.

## Scope

In scope: anything in this repository that lets somebody reach an album, a
photo, a guest's details or a host's account that they should not, or that
takes a deployment down.

The areas most worth looking at, because they are where this application's real
risk sits:

- **Album isolation.** Every photo, guest and quest belongs to one event. A
  message or request that crosses between two weddings is the worst class of
  bug here.
- **Guest identity.** Guests are anonymous and anchored to a client-supplied
  device fingerprint, which is deliberately not a secret. Minting a *durable*
  credential for somebody else's guest identity is a vulnerability; being
  counted against their upload quota is the documented trade-off.
- **Photographer ingest.** An ingest key is a bearer credential accepted over
  both HTTP and FTP.
- **Tier gating.** The client hides paid features; the server is what enforces
  them. Reaching a paid feature without the plan is in scope.
- **Retention and deletion.** This code permanently destroys photographs.
  Anything that causes it to delete more, or sooner, than it should.

Out of scope: findings that require a maintainer's own credentials, reports
generated by a scanner with no demonstrated impact, and missing headers on
endpoints that serve no sensitive data.

## Supported versions

`main` only. There are no release branches, and no backports.

## What is already known and deliberate

Reading these first will save you time:

- `.env.example` and `docker-compose.yml` contain placeholder secrets. They are
  public on purpose, and the application **refuses to start in production** if
  it finds one in `JWT_SECRET` (`server/lib/config.ts`).
- Plain FTP refuses to start in production without an explicit
  `FTP_ALLOW_PLAINTEXT`, because an ingest key would otherwise cross the
  network in clear.
- `RETENTION_ENFORCED=true` deletes albums. It is gated on the host having been
  warned, and on that warning not having bounced.
- The dependency audit gate (`npm run audit:ci`) runs in CI with an allowlist
  that is currently empty. A new advisory fails the build.

`docs/SECURITY.md` describes how the authentication, tier gating and storage
model actually work. It is architecture documentation rather than a disclosure
policy, and it is the fastest way to understand the system before testing it.
